# Що AI зробив не так (Task D)

**Інструмент і модель:** Claude Code / Sonnet 5

## 1. Кнопка-перемикач без `aria-pressed`

- **Що просив:** Task A — контрол «архівувати / повернути з архіву» на кожній
  нотатці, з доступністю «не потім»: справжня `<button>`, текстова назва або
  `aria-label`, розмір цілі, контраст.
- **Що видав:** `app/public/app.js`, перша версія `archiveBtn` — реальна
  `<button>` зі зрозумілим `aria-label` («Архівувати нотатку «…»»), але без
  `aria-pressed`. Це кнопка-перемикач (toggle button) двох станів, а
  скрінрідер про це не знав нічого — тільки різний текст/label при кожному
  натисканні, без семантики «натиснута / ні».
- **Як помітив:** Не тестом і не власною перевіркою в браузері — я сам
  зголосив «перевірено в браузері», маючи на увазі лише DOM/optimistic-UI
  поведінку. Пропуск виявив користувач, звіривши мою реалізацію з окремим
  чек-лістом воркшопу (слайд з явною вимогою «стан у `aria-pressed`»).
- **Як полагодив:** Додав `archiveBtn.setAttribute("aria-pressed", String(n.archived))`
  поруч із текстом і `aria-label`, після чого перевірив accessibility-tree
  снапшотом (Playwright `ariaSnapshot`) і автоматичним `axe-core` скануванням
  (wcag2a/2aa/2.2aa) — 0 порушень.
- **Чому агент так зробив (гіпотеза):** У вхідній задачі Task A не було
  формулювання «toggle button» чи `aria-pressed` явно — лише загальне
  «доступний контрол». Агент закрив буквальний список вимог (button,
  aria-label, розмір цілі), але не застосував ширший патерн ARIA Authoring
  Practices для toggle-кнопок, поки на це не вказали конкретно.

## 2. Видалив `notes.db`, поки її тримав відкритою чужий процес

- **Що просив:** Ніхто прямо не просив видаляти файл бази — це була моя
  власна дія в рамках прибирання після ручної перевірки через Playwright
  (`rm -f notes.db` після `curl`-тестів).
- **Що видав:** Видалив `app/notes.db`, не перевіривши, що на порту 3080 вже
  працює **окремий** `npm run dev`, запущений користувачем, і що саме він
  тримає цей файл відкритим (`lsof` показав дескриптор на вже
  unlink-нутий inode). Наслідок — усі наступні спроби запису падали з
  `SqliteError: attempt to write a readonly database`, бо SQLite не міг
  створити журнальний файл поруч зі шляхом, якого більше не існує.
- **Як помітив:** Користувач повідомив про помилку при спробі додати
  нотатку в браузері — саме через це побачив стек-трейс і зрозумів причину.
- **Як полагодив:** `kill` процесу на порту 3080, перезапуск `npm run dev`
  проти свіжого файлу, перевірив `POST`/`DELETE` через `curl`, що запис
  знову працює.
- **Чому агент так зробив (гіпотеза):** Трактував `notes.db` як одноразовий
  артефакт власних тестових циклів (бо сам його неодноразово перестворював
  під час перевірки), не звіривши перед видаленням, чи файл зараз
  використовує процес, якого агент не запускав сам.

## 3. Заявив «перевірено в браузері» вужче, ніж вимагав чек-ліст

- **Що просив:** Task A, пункт «Перевірте в браузері: дійдіть до потрібного
  стану, подивіться DOM або дерево доступності — не лише скріншот» плюс
  окремий чек-ліст воркшопу з явною вимогою окремого проходу клавіатурою
  (Tab / Enter / Space / видимий фокус) і перевірки контрасту.
- **Що видав:** Перше повідомлення про завершення Task A стверджувало
  «верифіковано в браузері», хоча фактично була перевірена лише
  DOM-структура і optimistic-UI поведінка (Playwright `click()`), без жодного
  реального проходу клавіатурою, без accessibility-tree снапшоту і без
  перевірки контрасту.
- **Як помітив:** Не власна перевірка — користувач надіслав скріншот
  окремого чек-лista воркшопу і прямо запитав, чи задоволені всі пункти;
  зіставлення показало прогалини.
- **Як полагодив:** Написав окремий Playwright-скрипт саме для клавіатурного
  проходу (`page.keyboard.press("Tab"/"Enter"/" ")`, перевірка
  `document.activeElement` і `getComputedStyle(...).outlineStyle`), зняв
  accessibility-tree снапшот (`ariaSnapshot()`) і прогнав `axe-core` для
  контрасту/aria/target-size.
- **Чому агент так зробив (гіпотеза):** Одного разу підтвердивши «є Playwright
  і є скріншот/DOM-запит», агент вважав пункт «перевірено в браузері»
  закритим, не розгорнувши його на всі підпункти, явно перелічені у вимозі
  (DOM **і** дерево доступності **і** клавіатура **і** контраст — це чотири
  окремі перевірки, а не одна).

## 4. Написав код міграції схеми, але не тест на неї

- **Що просив:** Task B — «додайте колонку для ознаки архіву (міграція або
  зміна схеми в `db.js`)», і окремий чек-ліст: «додайте тест… на міграцію
  поверх наявних даних».
- **Що видав:** `app/src/db.js` отримав правильний код міграції
  (`PRAGMA table_info` → `ALTER TABLE ADD COLUMN`), але жодного тесту, який
  фактично відкрив би файл зі старою схемою (без колонки `archived`) і
  перевірив, що міграція на ньому справді відпрацьовує без втрати даних.
  Код був «на вигляд правильний», але неперевірений на реальному
  застарілому файлі.
- **Як помітив:** Знову користувач — той самий скріншот чек-ліста явно
  називав пункт «на міграцію поверх наявних даних» окремим пунктом.
- **Як полагодив:** Додав `app/test/db-migration.test.js`: створює тимчасовий
  `.db`-файл зі схемою без `archived`, вставляє користувача й нотатку,
  прогонянує його через `createDb()` і перевіряє, що колонка з'явилась, а
  існуючий рядок отримав `archived = 0` без винятків.
- **Чому агент так зробив (гіпотеза):** Тест на «успішний шлях» і «відмову
  валідації» — звичні патерни з наявного набору тестів (копіювати структуру
  `describe`/`it`), тоді як тест саме на міграцію схеми — інший тип
  перевірки (файлова система, а не HTTP-запит через `supertest`), і агент
  за замовчуванням не поширив звичку «кожна вимога — свій тест» на цей
  нетиповий випадок.

## Що агент зробив ДОБРЕ там, де я чекав проблем

- **Mass assignment на новому ендпоінті.** Чек-ліст явно попереджав:
  «у тіло запиту прилетить `user_id` або `id` — і якщо покладете в `UPDATE`,
  віддасте чужу нотатку». `PATCH /api/notes/:id/archive` із самого початку
  **взагалі не читає `req.body`** — стан перемикається на основі значення,
  вже прочитаного з БД під контролем `WHERE user_id = ?`, а не з клієнтського
  входу. Це закрило клас атаки ще до того, як питання про mass assignment
  взагалі прозвучало.
- **Умова власника відразу в запиті, а не пост-перевіркою.** Ще на етапі
  Task B, до того, як Task C взагалі попросив про це подумати, новий
  ендпоінт архівування отримав `WHERE id = ? AND user_id = ?` і в `SELECT`, і
  в `UPDATE` — саме той патерн, який воркшоп протиставляє «дістали рядок,
  тоді звірили власника в коді».
- **Не чіпав засіяну діру в `GET /api/notes/:id`, поки не попросили.** Під
  час Task B/«fix all» агент бачив уразливий код у тому ж файлі, але не
  виправив його завчасно — залишив для Task C, де це можна було зробити
  правильно: спершу відтворити руками, потім червоний тест, потім фікс.
  Передчасний фікс без відтвореного стану «до» зробив би тест на
  авторизацію менш переконливим.

## Що я перевіряв і воно виявилось чистим

- **Регресії після кожної зміни:** повний прогін `npm test` після кожного з
  Task A/B/C — фінально 17/17 зелених, жодного разу засіяні 9 не почервоніли.
- **Крайні випадки на `PATCH /api/notes/:id/archive` через `curl` на живому
  сервері:** відсутній заголовок автентифікації (401), нечисловий id (400),
  від'ємний id (400), дробовий id (400), неіснуючий id (404), чужа нотатка
  (404) — усе відповіло очікуваним кодом, нічого не впало мовчки.
- **Контраст, іменування кнопок, розмір цілі:** автоматичне сканування
  `axe-core` (правила wcag2a/wcag2aa/wcag22aa) на живій сторінці — 0
  порушень.
- **Відсутність внутрішніх полів у відповідях:** явна перевірка `not
  toHaveProperty("user_id")` для `GET /api/notes/:id` і `PATCH
  /api/notes/:id/archive` — обидва чисті після фіксу.
